# AI Engineering

- faculty: Engineering Faculty
- owner: appointed Dean of Engineering Faculty
- status: public architecture approved; Student delivery begins only after Course Entry
- direction: production-oriented AI/ML systems engineering
- primary implementation language: Python
- estimated learning volume: approximately 500 ± 100 hours
- intended intensive horizon: approximately 4 months, adapted to Student capacity and verified prior competence

## Course purpose

Develop the ability to engineer production AI systems by extending strong software-engineering foundations into machine learning, model engineering, retrieval/knowledge systems, agentic systems, production AI, cloud/AI platforms, and MLOps.

The Course is a route of competencies. It is not a frozen collection of pre-generated lessons.

## Language boundary

Python is the only programming language intentionally developed as a learning track in this Course. Other languages may appear when interacting with existing systems, but PHP, Node/TypeScript, C++, or other languages do not become parallel learning tracks merely because a project uses them.

## Module framework

### 1. Python AI Engineering

Value: establish Python as the working engineering language for AI/ML systems and close gaps that would block later Modules.

### 2. ML & Model Engineering

Value: build the foundations required to understand, train, evaluate, and engineer machine-learning models rather than only call AI APIs.

### 3. Retrieval, RAG & Knowledge Engineering

Value: engineer systems that retrieve, structure, ground, and use external knowledge reliably.

### 4. Agentic AI Engineering

Value: design and implement agentic systems with explicit responsibilities, tools, state, orchestration/delegation, evaluation, and failure boundaries.

### 5. Production AI

Value: turn AI capabilities into reliable production software: interfaces, structured outputs, validation, evaluation, observability, safety/guardrails, error handling, provenance, versioning, and human-in-the-loop where appropriate.

### 6. Cloud & AI Platform Engineering

Value: operate AI workloads as production infrastructure and connect model/application concerns with cloud, deployment, serving, scaling, and platform engineering.

### 7. MLOps & Model Lifecycle

Value: manage the complete lifecycle of models and AI systems: experiments, artifacts, registries, pipelines, deployment, monitoring, evaluation, change, and reproducibility.

## Delivery layers

The public Course architecture and a Student's current delivery state are
separate:

1. `pre-course/` contains orientation, bounded bridges, and independent entry
   diagnostics before Course/Module delivery starts.
2. `modules/` contains the stable Module contracts. A Module may have no
   detailed Themes until the Dean opens it for a Student or cohort.
3. `modules/<module>/themes/` contains detailed Theme and Lesson material only
   after the relevant Module handoff.

The existence of a Module contract does not mean that the Student has started
that Module. Course Entry and Module Entry are explicit Dean decisions based on
accumulated evidence.

## Framework rules

- These seven Modules define the current Course architecture, not complete Module syllabi.
- Each Module must acquire a public Entry Contract and Exit Contract before detailed teaching content is authored.
- Module adjacency is competency-based: completion of the preceding Module is not automatically required when the next Module Entry Contract is independently satisfied.
- A Module is a unit of educational value, not merely a folder of topics.
- Detailed themes and lessons are prepared near Module entry.
- Before Module entry, verified Student competence is evaluated when evidence is insufficient or stale.
- The Dean may skip, bridge, reorder where dependencies permit, or narrow a Module based on verified evidence; the Student is not required to consume material already mastered.
- Module detail may evolve as the field changes while the Course direction remains coherent.
- AI-assisted implementation rules and competence verification are governed separately by University policies and assessment workflows.
- Real projects may provide transfer/application contexts, but they do not replace independent evidence of competence. The Dean does not preassign a specific product by default; appropriate workers discover a suitable application context with the Student and return a persisted plan.
- Where a relevant external certification is intentionally adopted, preparation should be absorbed into the appropriate Module when possible and professionally justified; unrelated technology breadth is not added merely for completeness.
- Passing the internal Module examination does not necessarily complete the Student Module Enrollment. Required/recommended application or certification activities may continue inside that Student's Module plan.

## Content intentionally not fixed yet

This framework does not yet prescribe:
- complete theme lists;
- lesson counts;
- exact exercises or labs;
- exact external resources;
- exact assessment artifacts;
- detailed Theme/Lesson content.

Module Entry/Exit Contracts are intentionally a Dean-owned design layer between this Course framework and detailed content. They may be created/refined without generating teaching materials.

Those are created or refined through Module Entry and the relevant academic workflows.

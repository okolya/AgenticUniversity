# Module Design Workflow

Owner: appointed Dean of the Faculty.

Purpose: develop a Module in two distinct stages without confusing the stable competency contract with the Student-specific teaching path.

Dean-to-Lecturer and checkpoint handoffs in this workflow use
`university/protocols/learning-interaction-contracts.md`.

## Stage A — Module contract (may exist before a Student enters)

1. Dean loads the Course direction, target competencies, Module position, dependencies, and relevant current domain knowledge.
2. Dean may request subject input from Lecturer, practical-capability input from Laboratory Specialist, measurability input from Learning Analyst, and examinability input from Examiner.
3. Dean defines and approves only the stable Module frame:
   - purpose/value;
   - Entry Contract: minimum observable prerequisite competencies;
   - Exit Contract: observable Module Success Criteria;
   - broad competency areas;
   - hard dependencies, if any;
   - outcome strategy: professional application and external certification status (`required`, `recommended`, `none`, or `undecided`) where justified.
4. Entry criteria must be independently measurable without requiring proof that a particular earlier Module was consumed.
5. Exit criteria must be independently examinable without prescribing Themes, Lessons, exercises, labs, or materials.
6. When an external certification is intentionally adopted and known, ensure its relevant preparation requirements can be absorbed into the Module without adding unrelated breadth.
7. Stop. Do not generate detailed content merely to make the Module look complete.

## Stage B — Student-specific Module execution design (near entry)

1. Dean compares the Entry Contract with permitted verified Student evidence.
2. If evidence is missing, stale, contradictory, or uncertain, Dean requests measurement from Learning Analyst; Learning Analyst returns evidence only.
3. Dean determines entry, skip, bounded bridge, narrowing, or other permitted adaptation.
4. Dean and Student establish the initial coverage plan and short planning horizon.
5. Dean issues a **bounded pre-entry teaching sequence** for the current bridge
   or Module Entry target. It must state the target Entry Contract criteria, the
   ordered teaching slices or Themes, the allowed Lesson slots for each slice,
   the evidence checkpoint after each slice, and the stop/decision condition.
   The sequence ends when the Entry Contract is evidenced, when its slots are
   exhausted, or when the stated stop condition is reached.
6. Before a Theme is opened for delivery, Dean must approve its bounded Theme
   contract: one clear Theme outcome, explicit Success Criteria, scope
   exclusions, a finite Lesson map, a final practical/checkpoint result, and a
   stop condition. A Theme with only a topic label or an open-ended request is
   not ready to start.
7. Dean defines only the Theme framework currently needed to move this Student
   toward the Exit Contract. Later Themes may remain at contract level, but
   each must receive the same finite Lesson map before it opens.
8. Dean assigns the first Theme to an appointed Lecturer and hands over the
   approved Module contract, Student-relevant evidence, bounded teaching
   sequence, and coverage constraints.
9. Lecturer prepares the Lessons required by the handed-over sequence just in
   time. Lecturer may adapt explanation, examples, and depth inside the
   sequence, but may not add Lesson slots, extend the sequence, or redefine its
   stop condition. Any such need returns to Dean. The Lecturer's pre-entry work
   ends with an evidence handoff; the Lecturer does not independently declare
   Module Entry.
